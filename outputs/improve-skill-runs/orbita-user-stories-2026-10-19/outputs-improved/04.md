Esse pedido está fora do escopo desta skill.

A `orbita-user-stories` transforma um PRD, spec, estudo, transcrição de reunião
ou descrição verbal **em cards do board Jira SQO** — ela não escreve o PRD.
A regra está no próprio contrato da skill:

> **Out of Scope** — Esta skill NÃO faz:
> - Escrever ou redigir o PRD em si → use `/claude-system-builder` (sistemas)
>   ou `/lovable-prompt` (apps Lovable)

E, na mesma linha, no Cross-Skill Routing:

> - Se não houver PRD/spec disponível → recomendar `/claude-system-builder` ou
>   `/lovable-prompt` antes de continuar

Você pediu objetivo, métricas de sucesso, requisitos funcionais e
não-funcionais da comparação de pontos comerciais — isso é exatamente o
artefato de entrada desta skill, não a saída dela. Se eu redigisse o PRD aqui,
eu estaria inventando o requisito e, logo em seguida, gerando cards a partir da
minha própria invenção: a rastreabilidade do card apontaria para mim, não para
uma decisão do time. É o pior modo de falha possível para um board que agora
tem dev júnior consumindo esses cards.

## Para onde ir

| O que você quer | Skill | Quando usar |
|---|---|---|
| PRD/spec técnica da comparação de pontos (objetivo, métricas, RF/RNF, arquitetura, modelo de dados) | `/claude-system-builder` | É o caso aqui — a comparação de pontos mexe em API de análise + tela Angular, é software em repositório existente |
| PRD de um app novo para prototipar no Lovable | `/lovable-prompt` | Só se a comparação fosse um protótipo descartável fora dos repos do Órbita |
| Ainda não está claro se o problema/feature se sustenta (CSD, árvore de oportunidades) | `/product-discovery` | Se "comparar pontos" ainda é hipótese, não decisão |
| Validar se a dor de comparar pontos é real antes de especificar | `/problem-validation` | Se você quer o teste Go/No-Go antes de gastar PRD |

Recomendação: **`/claude-system-builder`**. A comparação de pontos comerciais
não é tela isolada — ela consome o resultado de análise que hoje sai do
`api-agent-orbita` e precisa de decisão sobre o que é comparável (score final?
breakdown por dimensão? camadas cruas?). Isso é spec de sistema, não de app
novo.

## O que eu faço assim que o PRD existir

Me traga o PRD (colado aqui, ou o caminho em `outputs/`) e eu sigo o fluxo
completo desta skill:

1. **Step 0** — leio o PRD + os estudos relacionados em `docs/confluence/` e
   decido se o card é do produto Órbita (então confiro os 3 repositórios) ou de
   outro produto do board SQO.
2. **Step 2** — quebro em épicos/cards INVEST, separando frontend
   (`webapp-orbita-angular`) de backend (`api-agent-orbita` /
   `api-orbita-nodejs`).
3. **Step 3** — rodo Grep/Glob real nos 3 repositórios antes de citar qualquer
   endpoint, controller ou componente. O que não existir vai como "Não
   localizado no código — confirmar com o time", nunca como caminho plausível.
4. **Step 3B** — mapeio efeitos de segunda ordem (quem mais consome o dado de
   análise, qual contagem muda, quem precisa ser avisado).
5. **Step 4** — escrevo cada card nas 8 seções exatas do template SQO:
   Contexto, Referências visuais, Caminho/rota, Escopo do card, Regras de
   negócio, Pontos em aberto, Critérios de aceite, Figma.
6. **Step 5** — passo cada card pelo subagente `(?_?) revisor-clareza-junior`
   até o veredito "pronto para o júnior".
7. **Step 6** — crio os tickets no projeto SQO - ÓRBITA (ou salvo em markdown
   se o Jira MCP não estiver conectado) e mostro o texto completo de cada card
   na resposta.

Nenhum repositório foi grepado nesta sessão e nenhum card foi gerado — não há
card a gerar enquanto a fonte de requisito não existir.

## Uma observação antes de você abrir o PRD

Vale checar se "comparação de pontos comerciais" já não esbarra numa decisão em
aberto que aparece nos estudos do Órbita: comparar dois pontos exige que o
score seja comparável entre eles, e o score hoje é montado com peso definido
pelos executivos, não pelo analista. Se o PRD assumir que basta mostrar duas
notas lado a lado, ele vai herdar essa discussão sem resolvê-la. Isso é tema de
`/product-discovery` ou `/problem-validation`, não desta skill — mas é melhor
saber antes de escrever o PRD do que descobrir em "Pontos em aberto" de cada
card depois.
