## Output — Input 03 (NotifyHub — Software)

**Classificação do PRD — NotifyHub**

| Critério | Evidência no PRD | Aponta para |
|----------|-----------------|-------------|
| Complexidade de backend | "Fila de processamento assíncrono com retry automático (3 tentativas, backoff exponencial)" | Software |
| Número de serviços | API REST + fila Bull/Redis + PostgreSQL + Dashboard + Webhook — múltiplos serviços | Software |
| Integrações externas | "Suporte a 4 canais: e-mail (SendGrid), SMS (Twilio), Slack webhook, WhatsApp (Meta API)" | Software |
| Infraestrutura | "Node.js + PostgreSQL + Bull (Redis) + Docker + GitHub Actions para CI/CD" | Software |
| Escopo do MVP | API REST + fila assíncrona + 4 integrações + webhook de status + dashboard — arquitetura multi-componente | Software |

**Destino proposto: Software — Claude Code**

**Porquê:** O PRD descreve uma plataforma com API REST, fila assíncrona (Bull + Redis), quatro integrações externas e webhook bidirecional. A stack declarada (Node.js + Docker + GitHub Actions) confirma que o produto exige um ambiente de software tradicional.

**Argumento mais forte para Lovable:** O Dashboard admin básico (monitoramento de volume e falhas) é a única superfície de interface do MVP e poderia ser prototipado no Lovable conectado a uma API externa — mas o PRD não separa o dashboard do backbone da plataforma.

**O que mudaria essa decisão:**
- Se o MVP fosse reduzido ao dashboard com dados mock, sem API e fila
- Se as integrações fossem eliminadas e o produto virasse CRUD de logs sobre Supabase
- Se a fila fosse terceirizada para serviço gerenciado sem código customizado (ex: Inngest, Trigger.dev)
